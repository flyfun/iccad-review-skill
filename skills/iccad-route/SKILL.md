# 双维路由与计划检查项

先定「查什么、查到什么深度」，再动手。顺序反了，后面所有意见都会长在错误的口径上。

## 维度一：工程模块

按**报告主题与核心结论**判定，不按关键词计数。

| 模块 | 典型报告 |
|---|---|
| M1 | 土石坝、水库（含除险加固） |
| M2 | 混凝土坝、拱坝、碾压混凝土坝 |
| M3 | 堤防、河道治理、山洪沟治理、侵蚀沟治理 |
| M4 | 水闸、泵站、输水建筑物（隧洞、渡槽、倒虹吸、管道） |
| M5 | 灌区、农田水利、节水灌溉 |
| M6 | 防洪评价（洪水影响评价）、涉河建设方案 |
| M7 | 水土保持方案 |
| M8 | 水资源论证、取水许可 |
| M9 | 环境影响评价、生态影响专题 |
| M10 | 大坝/水闸/泵站安全鉴定（出**类别**，不出方案） |
| M11 | 重大设计变更、建设方案复核 |
| M12 | 水工程建设规划同意书论证 |
| M13 | 河湖健康评价（出**等级**） |
| M14 | 幸福河湖建设实施方案 / 自评估（出**星级**） |

**M10~M14 不与 M1~M9 混用**：前者是鉴定或评价，产出等级/类别/星级，不套四阶段投资与概算逻辑；后者是设计，产出方案。

**M3 先分两子类**：
- 含山洪沟防洪治理 → 按山洪沟口径（防御标准、护岸与沟道整治、预警非工程措施）；
- 含侵蚀沟/小流域综合治理 → 按水土保持与侵蚀沟治理口径（分级、措施配置、措施投资占比）。
两类都套「堤防」口径是常见判错。

## 维度二：设计阶段

| stage | 判据 | 深度要求 |
|---|---|---|
| `proposal` | 项目建议书 | 必要性、规模初判、投资匡算 |
| `feasibility` | 可研 | 方案比选、规模论证、投资估算、经济评价 |
| `preliminary` | 初设 | 建筑物结构、施工组织、概算、征地移民 |
| `construction_doc` | 施工图/技施 | 细部构造、工程量、材料与施工要求 |
| `special` | 专项报告 | 按专项规程的章节与结论链 |
| `safety_appraisal` | 安全鉴定 | 复核计算、类别判定、处理建议 |
| `design_change` | 重大变更 | 变更理由、影响范围、投资变化 |
| `evaluation` | 评价评估 | 指标体系、赋分、分级 |

专项报告（M6~M9）**不套**四阶段投资与概算逻辑；评价类（M13/M14）**不套**方案设计逻辑。

## 生成计划检查项

1. 取本模块的候选检查项（见 [模块矩阵](references/module-matrix.md)），按项目实际筛选。
2. **并入通用项**：责任表与签署、资质、签章、目录页码、附图附表、版本一致性、规范号现行性。这些不是技术问题，但属于必查，不能因「不是技术」跳过。
3. 跨模块报告**全量加载**涉及模块，不只取主模块。
4. 去重、编号（建议 `C01…`）、写入 `planned_check_ids`。
5. 计划项少于 8 条时自查：是范围真的小，还是漏了通用项与篇章？

**禁止**为了门禁好看而只规划能查的项。查不了的写进计划，状态记 `unsupported` 或 `insufficient_input`，在报告缺口节单列。

## 与引擎领域判定的关系

确定性引擎按关键词计数判领域，已知存在偏差（灌区渠系报告常被判为水闸，从而套用水闸模块清单）。冲突时：

- 以本 Skill 的判定为准；
- 在 `scope_ref` 保留引擎原判（`engine_domain`）备查；
- 在报告中标注「模块来源：人工判定」。

## 输出与交接

`project.module`、`modules_extra`、`project.stage`、`planned_check_ids`，以及一份可读的清单（每项：编号、内容、适用依据、能力前提）。交各专业 Skill 执行。
