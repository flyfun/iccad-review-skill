# 规范索引与取条文方法

## 一、先取尺子，再下判断

本技能**不硬编码条文**。判定依据一律通过工具从规范库取。

**工具**：`scripts/spec_lookup.py`

**默认数据源 = 技能自带的条文库**（`references/sluice_clauses.json`）。
JSON 路径按**脚本所在位置**定位，因此在任何目录下调用都能找到，**不需要本机任何外部路径**。

```bash
# 看自带库里有啥（唯一可靠的口径）
python spec_lookup.py --list-specs

# 取条文（关键词过滤）——默认走自带 JSON，无需任何附加参数
python spec_lookup.py --spec "SL 265" --q 闸顶高程
python spec_lookup.py --spec "SL 265,SL 744" --q 抗滑 --limit 30

# 指定别的 JSON（可选）
python spec_lookup.py --from-json other.json --q 抗浮

# 查"自带库之外"的规范：改用本机块库（可选，需 hydro_reviewer 源码树）
python spec_lookup.py --pkl "C:\Users\Administrator\水利审查工具\specs_db\chunks.pkl" --spec "SL 274" --q 坝坡
```

**自带条文库**：`references/sluice_clauses.json` —— **12 部 / 9,766 块**，其中 **7,172 块带条款号**（清单见第二节）。

**备用数据源（可选）**：`C:\Users\Administrator\水利审查工具\specs_db\chunks.pkl`（全库 41,833 块 / 62 部）。
块库为 pickle 格式，对象类 `SpecClause` 定义在 hydro_reviewer 的 `src/`，读取需源码树在 `sys.path`（脚本会自动加）。
**只有要查自带库之外的规范时才需要它**；这三条默认路径为本机专属、换机器即失效。
可用 `--pkl` / `--src` 参数覆盖，或设环境变量 `SPECS_DB` / `HYDRO_SRC`。

**限值表（另一条通道）**：规范原文的**参数表**（容许安全系数、坡降、f 值、应力比、安全加高等）
在条文库中**未被提取**（只存了表号与表名）。这些限值另从原始 docx 提取，固化在
**`references/sluice_tables.md`** —— 判定取限值查这里，与 `calc_stability.py` / `calc_hydraulics.py`
内联限值一致。

> 注意区分：**条文的文字**走 `spec_lookup.py`（自带 JSON / 可选块库）；**限值表格**走 `sluice_tables.md`（docx 提取）。
> 两者都不可凭记忆写。

**查条文三条纪律**（2026-10-16 实测；写法不当会让载入量差几十倍，甚至查漏）：

| 纪律 | 错例（实测） | 正解 |
|---|---|---|
| **优先词组、少用单字** | `--q 抗` → **53 条 / 5,331 字符** | `--q 抗滑稳定安全系数` → 12 条 / 2,390 |
| **条号用纯条号，别带"表"字** | `--q 表7.3.13` → 仅 **1 条（会漏）** | `--q 7.3.13` → 4 条（库内 `clause` 字段不含"表"字） |
| **认准规范编号再查** | 凭印象写编号常查空（如 SL/T 前缀有无"T"） | 先 `--list-specs` 看准编号，再用该规范原文用词 |

**输出约定**：诊断信息（`loaded` / `matched` / `exported`）一律走 **stderr**，**stdout 只有条文正文** ——
可直接管道或计量载入量；要连诊断也静默，加 `--quiet`。

**子串匹配的局限**：`--q` 是**字面包含**匹配，不是语义检索——命中块里常混入只是"提到该词"的低相关条文，
**取回后须人眼挑出真正对口的那条**，不要整块照抄进审查意见。

## 四、引用纪律（硬规则，违反即为错误结论）

1. **条款号一律来自 `spec_lookup.py` 输出或已固化的 JSON**，不凭记忆写。
   （实证：本文件上一版凭记忆写的 `SL 191`、`SL 379`、`SL 725`、`SL 44` 与库内实际**全部不符**——库里是 `SL/T 191`、`SL/T 386`，且没有 SL 725、SL 44。）
2. **取到条文原文再判**。写"违反 SL 265 4.2.4"之前，先跑一次工具把 4.2.4 原文调出来核。
3. **手册给的是经验区间，不是强制条文**。审查意见写"手册推荐 / 工程惯例"，**不得写成"违反规范"**。
4. **数值型条款必须保真**。安全系数、超高、阻水比、压实度、渗透系数等指标型条款是审查核心，检索与去噪时不得被过滤掉。
5. **条款粒度可到子项**。如"4.2.22 中第 3 条"，引用时给到可核验的最小粒度。
6. **不确定就标"待核"**，不编、不凑。
7. **规范原文属内部资料**，本 skill 的固化数据仅供本机审查使用，不外传。

## 五、易踩的坑

1. **版本替代**。`SL 203 → GB 51247`（抗震）。报告引旧版且新规范已强制 → 属问题。
2. **编号变体**。`SL 265` ≡ `SL/T 265` ≡ `SLT 265`，`/T`、强制↔推荐 归一化后视为同一规范。
3. **主评价规范豁免**。报告的主评价规范（洪水影响评价的 SL/T 808）在相关性过滤中应显式豁免，不得当噪声剔除。
4. **编制规程 ≠ 设计规范**。SL/T 618/619 管"报告写什么"，用它判"工程怎么做"会判错。
5. **库态只认实测**。块数与部数用 `--list-specs` 点数，不要用文件时间戳判断库有没有更新。
6. **公式图形化**。SL 265 原文的公式多为嵌入图片，条文库只存了符号说明文字。取公式须回原始 docx 提图识读，**不能凭"公式编号"猜形式**。
7. **强条别漏判**。4.2.4 / 4.2.5 / 7.3.13 / 7.3.14 是强制性条文，"不满足"与"违反强条"是同一件事，措辞与严重度不能降格。
