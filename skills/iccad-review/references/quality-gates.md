# 质量门禁与放行条件

门禁只回答一个问题：**这份工作记录是否具备交人工审签的条件**。它不回答工程是否安全，也不回答报告是否合格。

## 三道闸门

| 命令 | 检查什么 | 通过意味着 | 不通过意味着 |
|---|---|---|---|
| `validate_review.py review.json` | 结构、枚举、引用、日期、状态关系、数值复算 | 记录自洽，可以继续工作 | 记录本身有错，先修记录再谈结论 |
| `… --verify-files` | 上述 + 所有来源位于允许目录内、字节哈希一致 | 记录指向的确实是本次资料 | 有来源被替换、移动或未收到 |
| `… --gate` | 上述 + 审签准备条件 | `ready_for_human_signoff` | 列出阻塞项，逐条解决 |

退出码：`0` 通过；`2` 有错误；`3` 结构有效但仍有阻塞（仅 `--gate`）。

**工作稿不需要清空阻塞项**。中途生成 Markdown 报告是正常用法，报告会如实标注待复核与缺口。只有对外提交审签材料时才要求 `--gate` 通过。

## `--gate` 的阻塞条件

1. **计划未执行**：`planned_check_ids` 中的项没有对应 check。计划项不得执行后删除。
2. **计划外执行**：存在不在 `planned_check_ids` 中的 check。先纳入计划，再执行。
3. **未求值**：检查项状态为 `insufficient_input`、`unsupported`、`unverified_basis`、`error`。
4. **依据未确认**：`evaluated` 的检查项引用了 `status=unknown` 或 `applicability≠confirmed` 的依据；被替代/未生效的依据缺 `transition_ref`。
5. **规则不可执行**：`evaluated` 的检查项引用了 `status=draft` 的规则。
6. **疑点未处置**：`review.status=pending`。
7. **未闭环**：`closure.status` 为 `open`/`response_submitted`/`recheck_required`；`P1` 疑点未 `closed` 或 `not_applicable`。
8. **闭环证据不足**：`closed` 缺回复、修订来源或针对**本轮 baseline** 的复查记录。
9. **结论未记录**：`conclusion.status=pending` 或缺失。

## 六个常见放行误区

| 误区 | 为什么不行 | 正确做法 |
|---|---|---|
| 「只规划能查的项，门禁就过了」 | 计划清单来自范围与专业矩阵；缩范围等于缩审查 | 计划项写全，查不了的记 `unsupported` 或 `insufficient_input`，在报告第五节单列 |
| 「材料不足就先标通过」 | 未知不等于合格 | 记 `insufficient_input`，并在缺口清单说明缺什么、谁来补 |
| 「设计单位回复了就算闭环」 | 回复不是整改，上传不等于修改 | 需要修订来源 + 人工复查记录 + 针对本轮基线的复查证据 |
| 「上轮已提过，这轮不必再记」 | 条数变少不等于变松；没有对账一定是漏 | 保留问题 ID，逐条标注保留/合并/升级/误报 |
| 「引擎扫过没报，说明没问题」 | 引擎只覆盖规则可判定项，且存在系统性误报与漏报 | 引擎候选只是起点，须按计划清单人工审查 |
| 「AI 写结论更快」 | 结论是审签责任，不是文本生成 | `conclusion` 只记录人工结论，AI 留空 |

## 范围缩减必须留痕

确因委托范围调整而缩减检查项时：

- 在 `checks` 中保留该项，状态记 `not_applicable`，`reason` 写明**依据**（委托书条款、会议纪要、批复范围）；
- 在报告中单列，不得静默删除；
- 缩减后不得对外宣称「已全面审查」。

脚本无法判断范围是否合理，只能保证缩减是**显式**的。

## 合成记录的限制

`mode=synthetic` 的记录：

- 只能用于流程演练、培训与回归测试；
- 依据编号以 `EX-` 开头或 `authority/status=synthetic`，在 `mode=project` 中会被判为错误；
- 其 `ready_for_human_signoff` 不代表任何真实工程具备审签条件。
