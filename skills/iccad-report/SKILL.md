# 审查意见书与审签准备

报告不是把疑点排个序。它要回答三个问题：**查了什么、查出什么、还有什么没查**。

## 输入与边界

`review.json`（完整记录）、依据清单、覆盖统计、闭环状态、人工处置记录。

生成的是**内部工作稿**。正式意见书需院内模板、编号、责任人签署与用印；本 Skill 不签发，也不代替审签。

## 报告结构

| 章 | 内容 | 要点 |
|---|---|---|
| 一 | 审查概况 | 项目、等别、模块、阶段、基线、依据基准日、范围、处理环境 |
| 二 | 覆盖统计 | 计划项数、已求值、不适用、缺口；疑点按重大/一般/建议分布 |
| 三 | 审查意见 | 逐条：问题、依据、证据定位、数值比对、建议、处置与闭环状态 |
| 四 | 必查项核查声明 | 逐项状态与结论，**不许只写「已核查」** |
| 五 | 未覆盖与缺口 | 材料不足、能力不支持、依据未核验；依据缺口单列 |
| 六 | 结论 | 人工结论（通过/修改后通过/不通过）+ 记录人与记录号 |
| 附 | 依据清单 | 编号、名称、条款、层级、强条属性、状态、适用性 |

生成命令：

```bash
python3 <iccad-review目录>/scripts/render_report.py review/review.json --output review/report.md
# 需要同时核验来源哈希时
python3 <iccad-review目录>/scripts/render_report.py review/review.json --verify-files --root <资料根目录> --output review/report.md
```

## 意见写法

每条意见四件事缺一不可：**在哪、是什么、凭什么、改什么**。

- 「在哪」：章节号/表号/图号 + 原文摘录（逐字，不改写）。
- 「是什么」：事实陈述，不写「设计不合理」这类评价。
- 「凭什么」：依据编号 + 条款；外部依据注明「依据来源：文件 § 定位」。
- 「改什么」：可执行动作（补计算、统一取值、修改控制指标）。

**不要**写「建议进一步核实」了事——那是没查到位的表现；确实无法判断的，记 `insufficient_input` 并列缺口。

## 结论三级

| 结论 | 适用 | 记录要求 |
|---|---|---|
| 通过 | 无疑点或仅个别建议 | 仍需人工签署 |
| 修改后通过 | 有需修改的一般问题，重大问题上已闭环 | 列明修改项 |
| 不通过 | 存在未解决的重大问题（P1） | 列明原因与重报要求 |

AI **只建议、不填写**；`conclusion` 只记录人工结论。

## 审签前自检

```bash
python3 <iccad-review目录>/scripts/validate_review.py review/review.json --gate --root <资料根目录>
```

- [ ] 退出码为 0（`ready_for_human_signoff`）
- [ ] 每条意见都有至少一条证据与一条依据（或明确的工程判断标注）
- [ ] 必查项声明表无空白项
- [ ] 缺口清单与正文表述一致，未把未查写成已查
- [ ] 意见编号连续，与批注版逐条对应
- [ ] 结论与意见分布不矛盾（有 P1 未闭环却写「通过」是最典型的硬伤）

## 批注版

需要退回修改的场合，意见要挂到原文对应位置（**逐条**，不是逐类）。要求：

- 每条意见在原文有唯一锚点，引文逐字匹配；
- 意见书第 N 条 = 批注「第N条」，编号体系一致；
- 无法定位的意见落附录，**不允许静默丢弃**；
- 交付前核对覆盖数（N/N），有缺口先修引文再交付。

## 不做什么

- 不输出「工程已通过审查」的表述；`ready_for_human_signoff` 只表示记录具备审签准备条件。
- 不按文件扩展名判断效力：Markdown、DOCX、PDF 都只是载体。
