# 设计回复与整改闭环复查

闭环的判据只有一个：**修订稿里确实改了，并且有人复查过**。回复、承诺、上传附件都不算。

## 输入与边界

上一轮疑点台账、设计单位回复、修订稿与修订说明、图纸目录变化、必要的计算书更新。

不替设计单位改稿，不代替专业责任人做技术判断；只维护记录的真实性与可追溯性。

## 问题编号必须稳定

- 同一问题跨轮次沿用同一 `findings.id`。
- 合并两条问题时，保留主 ID，把被合并 ID 记入备注，不新起编号。
- 判定为误报时，不删除记录：改处置为 `not_applicable` 并写明理由与确认人。
- 新问题用新 ID，并在备注注明「本轮新增」。

## 四个状态，不要混用

| 记录 | 含义 | 不等于 |
|---|---|---|
| `review.status=adopted` | 人工确认该疑点成立 | **不等于**已整改 |
| `review.status=undetermined` | 尚需专业判断 | 不等于不成立 |
| `closure.status=response_submitted` | 收到回复 | 不等于已修改 |
| `closure.status=closed` | 已修改且有本轮复查记录 | 不等于整体合格 |

## 闭环必须齐备的四项

1. `response`：设计单位的实际修改说明（不是承诺）。
2. `revision_source_ids`：修订稿来源及哈希，指向真实文件。
3. `recheck`：复查人、时间、记录号、**本轮 `baseline_id`**。
4. `recheck.evidence`：具体位置与内容（「5.2.1 已改为 98%，并补充碾压试验参数表」）。

缺任一项，`--gate` 都会阻塞。这是有意为之：**最容易出的错就是把「回复了」当成「改好了」**。

## 对账方法

按 ID 逐条展开成核对工单，对每条给出候选定位（表号/图号/章节号权重更高，长词组次之），再逐条裁决：

| 裁决 | 条件 |
|---|---|
| 保留 | 修订稿中问题仍在，措辞可换但实质未改 |
| 合并 | 与其他条指同一处同一问题 |
| 升级 | 修改引入新问题，或原问题范围扩大 |
| 误报 | 原判断有误，写明依据 |
| 补录 | 修订引入的新问题 |

条数变少不等于变松；**没对账一定是漏**。对账完成后在报告「总体评价」末尾留一行回归声明：保留 / 合并 / 升级 / 误报 / 补录各多少条。

## 常见错误做法

- 看到回复里有「已修改」就标 `closed`，未核对修订稿。
- 用新版本覆盖旧结论，旧证据丢失，无法回溯。
- 跨基线复查（用上一轮基线判断本轮闭环）。
- 只核正文不核图纸与工程量，修改只改了一处。

## 输出与交接

更新 `findings[].review` 与 `findings[].closure`，产出对账表（ID、上轮表述、本轮状态、证据位置、裁决）。交 `$iccad-report` 汇总；`P1` 未闭环项必须在报告首页显著列出。
